# Known defects and accepted deviations

This register lists defects that exist today, and deviations we have accepted on
purpose. Read it before you "fix" code near one of them, so that you know what is
already there and do not bring back something removed on purpose. Each entry says how
it was checked and whether it is **open** (should be fixed) or **accepted** (kept on
purpose, with the reason).

Last reviewed: 2026-11-24.

## Pipeline and scheduling

| # | Status | Defect | Evidence / reason |
|---|---|---|---|
| D1 | Open (operator) | **Renovate is configured but not installed.** `renovate.json` exists, but no Renovate app or workflow runs, so no dependency PRs are opened. | No Renovate workflow in `.github/workflows/`; the owner is installing it. |
| D2 | Open | **Scheduled workflows auto-disable after 60 days without repository activity** (GitHub behaviour for public repos). If that happens, the weekly rebuild in `build.yml` and the Trivy DB mirror stop silently, and the rolling tags stop getting OS patches. | Documented GitHub behaviour. The keepalive is the Renovate commits once D1 is done. Until then, re-enable the workflows in the Actions tab if they are disabled. |
| D3 | Accepted | **One failing variant blocks the weekly publish of all nine.** `publish` needs the whole `build-scan` matrix, so a single blocking finding in one distro/flavor/arch holds back every variant's OS patches. | `build.yml`, `publish.needs: [ignore-expiry, build-scan]`. Accepted: pip-audit and OSV-Scanner run only in `build-scan`, and gating publish on them per variant would need a matrix-aware `needs`. |
| D4 | Accepted | **Failed verifies leave orphan untagged digests on GHCR.** `stage` pushes by digest before `verify`. If verify fails, that digest stays in the package, untagged and unsigned, and can be pulled by digest. | `publish.yml`, the `stage` job. Accepted: no tag or signature ever points at it, and a "delete untagged" GC on GHCR would also delete cosign signatures and attestations, which are stored as untagged manifests (see the design spec, "Risks"). |
| D5 | Accepted | **The Trivy DB can be up to a week old.** Trivy reads the weekly mirror (`trivy-db-mirror.yml`, Mon 03:00 UTC) through `TRIVY_DB_REPOSITORY`; it does not use `--skip-db-update`. Grype pulls its DB live from Anchore and is not mirrored. | `trivy-db-mirror.yml`; the Trivy steps' `env`. Accepted in exchange for not trusting the upstream Trivy DB at scan time. Grype, as an independent DB, catches what a stale Trivy DB misses. |
| D6 | Accepted | **Dated tags are fixed by pipeline policy, not by the registry.** `promote` checks that `<core>-<flavor>-<distro>-<YYYYMMDD>` is absent and then creates it (check-then-create). GHCR and Docker Hub tags are mutable, so anyone with push rights, or a writer racing the check, could still move one. Only a digest is truly immutable. | `publish.yml`, the promote step; the docs say "created once, skipped if it exists" rather than "immutable". Runs on `main` are serialised by the `build-${ref}` concurrency group, and each variant writes distinct tags. A same-day rerun keeps the first build's dated tag and logs a notice. |
| D7 | Accepted | **The digest assertion runs after the tags move.** `promote` asserts that every tag resolves to the verified digest *after* `imagetools create`. It detects a mismatch and fails the run, but cannot undo the tag move. | `publish.yml`. Break-checked locally: tagging a different digest fails with `… resolves to sha256:…, expected verified digest sha256:…`. A registry cannot create a tag conditionally. |
| D8 | Open | **The `$/` self-repository syntax is not adopted.** zizmor's `self-repository` audit is suppressed inline on the `uses: ./.github/workflows/publish.yml` call. | `build.yml`, the `publish` job. The pinned actionlint 1.7.12 rejects `uses: $/.github/workflows/publish.yml` ("is not following the format … nor \"./path/to/workflow.yml\"", checked 2026-11-23). It is also unverified how `$/`, which resolves to the running commit, changes the OIDC `job_workflow_ref`, and so the documented signer identity `…/publish.yml@refs/heads/main`. Switch only after actionlint supports it and a test run shows the claim. |
| D9 | Open | **The yq digest in `scripts/check-ignore-expiry.sh` is not tracked by Renovate.** Renovate tracks `image@sha256` pins in workflows and pre-commit, not in shell scripts. | `scripts/check-ignore-expiry.sh`, `YQ_IMAGE`. Bump it by hand, or add a Renovate regex manager for it. |
| D10 | Open | **The `add-image-variant` skill does not know about `publish.yml`.** A new distro or flavor must also be added to `publish.yml`'s input allowlist (the stage job's "Validate inputs" step) and to the `publish` matrix in `build.yml`. | `.claude/skills/add-image-variant`, owned outside this change. |
| D11 | Accepted | **A re-run of an older run is refused; a first attempt always publishes its own commit.** On a re-run (`github.run_attempt > 1`), `promote` requires `github.sha` to equal `main`'s current HEAD (`gh api …/git/ref/heads/main`, failing closed on an API error), so re-running an old run cannot move the rolling tags backwards. That includes re-running an old run's failed jobs. If `main` has moved, even by a docs-only commit, re-run the latest run or dispatch `build.yml` on `main` instead. First attempts skip the check, because the `build-${ref}` concurrency group serialises them and a newer run evicts an older pending one. An unconditional check would make an in-flight run refuse whenever a commit that triggers no build (filtered out by `paths`) lands mid-run, so nothing would ship. Because each of the nine variants checked independently, it could also leave a partial set. | `publish.yml`, the step "On a re-run, refuse unless this commit is main's current HEAD". Checked locally: attempt 1 with an older SHA gives rc 0; attempt 2 with the current HEAD gives rc 0; attempt 2 with an older SHA gives rc 1 ("refusing to promote"); attempt 2 with an API 404 gives rc 1; an empty attempt gives rc 1. |
| D12 | Accepted | **`promote` still runs some third-party code with signing credentials.** That code is `sigstore/cosign-installer` (which downloads the cosign binary), the attest actions, `docker/login-action`, `docker/setup-buildx-action` and `actions/download-artifact`, all SHA-pinned. No scanner or SBOM generator runs there; the SBOM comes from the separate `sbom` job and is integrity-checked before it is attested. | `publish.yml`, the `promote` job; `docs/supply-chain.md` §4 "SBOM trust chain". |
| D13 | Accepted | **The `sbom` job relies on anonymous GHCR pulls.** It has no registry login, so it works only while the `ghcr.io/d10scot/ansible` package is public. If the package becomes private, the job fails closed. | `publish.yml`, the `sbom` job. Deliberate: it keeps registry credentials away from syft. |
| D14 | Accepted | **`pip-audit --no-deps` silently skips lockfile lines whose environment marker does not match its interpreter** (python 3.13 in the pinned container). | pip-audit 2.10.1, 2026-11-23: `jinja2==3.1.2 ; python_version >= "3.14"` gave "No known vulnerabilities found"; without the marker, 4 PYSEC findings. The lockfiles have no markers today (`scripts/lock.sh` compiles per environment, without `--universal`), and `build.yml` now fails the step if any marker appears. |

## Images

| # | Status | Defect | Evidence / reason |
|---|---|---|---|
| I1 | Accepted | **The runtime images keep the OS package manager** (`apk` on Alpine, `apt-get` on Debian/Ubuntu) **and `pip`** in `/opt/ansible`. This is against the "no package manager in the runtime stage" hardening rule. | `docker run … core-alpine`: `/sbin/apk`, `pip 26.1.2`; `core-debian`: `/usr/bin/apt-get`, `pip 26.1.2`. Accepted because downstream users extend the image (extra collections, system packages). `pip` itself is being hash-pinned in a separate PR. |
| I2 | Accepted | **The Debian runtime ships perl**, pulled in as a dependency of `git`. | `core-debian`: `dpkg-query` shows git `Depends: … perl, liberror-perl …` and perl 5.40.1-6 installed. `git` is needed by `ansible-galaxy` and for git-sourced roles. |
| I3 | Fixed for new publishes | **Digests published before `publish.yml` carry one SBOM on the index, which describes only amd64.** syft resolved the index to the runner's platform. | `gh attestation verify oci://ghcr.io/d10scot/ansible:latest … --predicate-type https://spdx.dev/Document/v2.3`: package URLs carry `arch=x86_64` only. From the first `publish.yml` run on, the `sbom` job makes one SBOM per platform manifest (checked locally: the arm64 manifest gives `arch=aarch64`). Each is attested on its manifest and on the index. Old digests are not re-attested. |
| I4 | Accepted | **The Ubuntu runtime deletes `/usr/bin/pebble` (and `/var/lib/pebble`) from the base image.** The `ubuntu:26.04` base is a Canonical rock that ships pebble (a Go service manager), which no dpkg package owns, so `apt-get upgrade` can never patch it. The bytes remain in the base layer: scanners reading the merged filesystem honour the deletion, but anyone unpacking layers still sees the file. | 2026-11-24: Grype v0.97.1 matched 8 fixable HIGH Go stdlib CVEs (go1.27.3; fixed 1.26.11 / 1.27.4) in `/usr/bin/pebble` and failed every ubuntu leg of run 45453610450. Base config is `Entrypoint: null`, `Cmd: ["/bin/bash"]`, so nothing here uses pebble. A `dpkg -S` sweep of all executables on both arches found no other unowned ELF/Go binary. Drop the `rm` once Canonical packages or removes pebble and Grype stays clean without it. |

## Distribution and verification

| # | Status | Defect | Evidence / reason |
|---|---|---|---|
| V1 | Accepted | **Docker Hub carries no signatures or attestations.** `promote` signs and attests only on GHCR and copies just the image manifest to Docker Hub. The cause is that design choice, not a registry limitation. | Checked 2026-11-23 with cosign v3.1.4 on `docker.io/d10scot/ansible@sha256:f345…a2cd`: plain `cosign verify` gives `no signatures found`; with `COSIGN_REPOSITORY=ghcr.io/d10scot/ansible` it passes. `gh attestation verify oci://docker.io/…` passes too (it uses GitHub's attestation API by digest). See `docs/verify.md`. |
| V2 | Open | **With cosign v3, `cosign verify` is also satisfied by the attestation bundles.** By default it returned the provenance and SBOM bundles (each signed by the same workflow identity) rather than the legacy `.sig` signature; with `--new-bundle-format=false` it returned the `.sig`. Either way the signer is our workflow, but the check is not specifically the cosign signature. | Observed with cosign v3.1.4 against `ghcr.io/d10scot/ansible:latest` on 2026-11-23. Consider signing in the new bundle format, or documenting `--new-bundle-format=false`. |
| V3 | Accepted | **Digests published before `publish.yml` are SLSA Build L2, signed by `build.yml`.** | `docs/verify.md`, "Images published before the reusable workflow". Old digests are not re-signed. |
